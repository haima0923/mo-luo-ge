# 千问ETIMEDOUT定位（2026-11-16）

## 本次证据

v0.3.17上线后，用户实际截图曾成功，随后再次出现108秒、214秒等待接口响应后ETIMEDOUT。服务已核实为0.3.17、图片单次等待预算300000ms、思考关闭、端点为北京dashscope官方地址。这两次在应用预算之前返回底层错误，不能用继续延长图片等待时间解释或处理。

“等待接口响应”涵盖DNS、TCP、TLS、上传及等待响应头，单凭这条提示不能断言一定是DNS、IPv6、TCP建立失败或模型已经开始工作。此前服务器单轮三模式对照只说明默认连接流式当时成功，尚未排除路由、地址族、模型负载或其他阶段；撤销close未消除间歇问题。

## 仅做网络探测

`scripts/qwen-network-diagnostic.mjs`在用户服务器使用同一套Node运行时，进行以下操作：

1. 查看默认DNS排序、自动地址族选择及Node/Undici版本；解析官方端点A/AAAA，去重并最多取IPv4/IPv6各4项。
2. 使用Node原生fetch对公开models端点做两次无鉴权GET，记录连接开始、TLS完成、请求发送、响应头及耗时。
3. 对chat/completions发送一次无鉴权、虚构无效model的64KB合成POST，检查较大请求体的网络路径。没有Authorization，不请求有效模型。
4. 对每个解析地址做HTTPS GET，保持原官方主机名、Host、TLS SNI及证书验证，区分TCP、TLS和等待响应头阶段；不配置固定IP、DNS或hosts。

每项最多6秒，逐地址最多并行2项；脚本总上限95秒（包括对GET可达地址追加的无鉴权64KB POST）。HTTP401/403是本测试预期，表示已收到服务端响应，不代表正常模型Key无效。不会使用API Key、发送Authorization、调用有效模型、写数据库/草稿、改配置或重启服务。启动命令使用现有服务env文件是为了沿用Node网络运行设置，脚本只输出代理存在与否等布尔值，不输出环境值、代理凭据、接口正文或原始异常。

可通过`--url https://官方域名/compatible-mode/v1/models`指定已配置地域或工作空间端点；仅允许官方HTTPS模型列表地址。Cloud侧未鉴权GET已收到401，只能证明Cloud代理路径可达，不能替代用户服务器的直接链路检查。

## 如何使用结果

- 解析失败或各次解析差异，需要检查服务器DNS；不能直接用Cloud解析地址替换。
- 若只有部分IP/地址族失败，结合默认fetch的连接事件判断是否命中坏路径，再考虑保留官方主机名的连接选择/故障切换，不能仅凭IPv6探测失败就判定IPv6是根因。
- 如果TCP完成但TLS未完成，检查TLS路径；若TLS和request_sent都完成而没有响应头，则要继续区分上传/网关等待/上游服务，不能把已送出的请求当成安全的“未提交”自动重放。
- GET和64KB POST都快速返回401时，基础连通性当时可用，仍需针对原模型请求记录相同阶段证据；此探测没有验证OCR或模型生成。

前述阶段只交付定位工具；下文记录收到POST对照证据后准备的0.3.18应用修补。不因ETIMEDOUT盲目扩大自动重试，避免原请求可能已提交而重复消耗。

## 首次服务器报告后的修正

用户回传截图显示，至少一个IPv4连接完成TLS并发送了请求，另有IPv6地址报ENETUNREACH。截图未覆盖默认GET、POST及全部逐地址结果，尚不能确定正常请求超时由IPv6导致。

旧诊断脚本在报告输出后漏接TLSSocket的迟到error事件而异常退出。已为socket和request保留错误监听；成功、失败、截止后的迟到错误均不改写已完成结果。逐地址探测显式限定该地址族，避免与默认连接自动选择混淆。该修正只影响定位工具。

新版结束时输出一页摘要。加`--report-file /新建目录/report.json`可把完整安全报告保存为权限0600的文件，拒绝覆盖已有文件；保存时不输出原始响应或环境变量。提交摘要供分析时，需要同时看到默认GET、64KB POST和各地址的结果，不能只截最后一个IPv6错误。

### 第二次回传与真实socket复现

用户服务器回传：默认GET两次到6秒仍未返回头（最后事件request_sent），默认64KB POST到6秒仍未返回头；逐地址GET中39.96.198.249约1506ms、8.140.217.18约990ms收到401，8.152.159.24在waiting_headers截止，39.96.213.166在tls_handshake截止。IPv4路径也存在差异，不能只禁用IPv6或据此更换地域接口。每项6秒预算仅作短探测，未证明较慢路径永久不可用；两次默认GET不能证明原模型请求已失败于某个固定地址。

前次新增error监听仍未解决脚本崩溃。使用真实Node24 HTTPS和合成无路由IPv6地址复现：同步lookup回调先触发ENETUNREACH，https.request构造期间抛出TypeError（读取null的setServername），此时request尚未返回，遗留TLSSocket没有机会挂监听，继而进程退出。假socket测试未覆盖真实TLS构造时序。现将自定义lookup结果通过queueMicrotask异步返回，匹配系统DNS回调语义；真实独立子进程回归验证正确返回ENETUNREACH并正常退出，保留已有错误监听。

新增仅对GET已收到HTTP响应的地址逐个发送无鉴权64KB POST，用于区分GET路径正常与POST路径正常；每次保留官方hostname、SNI及证书验证，没有Authorization和有效模型。仍不修改运行中的应用，也不把已发送、未确认结果的模型请求自动重放。

## 2026-11-17 POST对照与0.3.18修补

修正后的诊断工具正常退出，完整报告保存成功。用户服务器Node24.22.0 / Undici7.29.1、DNS verbatim、自动选择地址族开启：默认GET两次约1623ms/3361ms收到401，默认64KB POST在6001ms截止（最后事件request_sent）。4个IPv4地址的GET均收到401（约973—5905ms）；相同地址POST只有8.140.217.18约2924ms收到401，另外三个6秒截止。IPv6两个地址直接ENETUNREACH。此次与此前GET结果有波动，因此不把某个地址写死，也不声称已经证实MTU、DNS排序、上游负载或某一IP是唯一根因。

0.3.18新增`lib/qwen-connection.mjs`，默认官方直连先用无密钥、无有效模型、无客户内容的64KB POST检测当前DNS地址（每族最多4个），选择最先完整收到401/403的候选，再通过该候选的HTTPS Agent发送正式分析。保留官方hostname/Host/SNI与证书验证。检测最多10秒，纳入原请求截止预算；成功结果缓存60秒，失败/过期由下一次调用重选。缓存退休等待在途请求完成，避免TTL或一个客户失败打断另一客户；候选检测可共享，正式输入和结果不共享。

新的默认传输使用Node内置HTTPS与Web Stream桥接，无第三方运行依赖；支持SSE、压缩JSON、取消和超时。正式请求开始发送后不自动重放，含断流和不完整输出。收到stop正常取消读取不会把健康线路判成故障。代理环境或显式`QWEN_CONNECTION_STRATEGY=default`沿用原fetch路径，避免绕过代理；同样不自动重放正式请求。未更换地域、模型或密钥；不改hosts或归档数据。

回归包含真实本机TLS证书验证、快慢线路竞争、正式请求计数、客户/智库共用链路、流中断、stop无EOF、取消隔离、TTL保护在途流、连接监听清理、gzip及重定向不转发；使用公开合成自签测试证书，未调用付费模型。浏览器以合成模型检查桌面与手机上的连接阶段、失败留图、无半截草稿与不自动重发。真实原图效果仍须服务器安装后验证；未鉴权探测成功不等同于模型识别成功。
